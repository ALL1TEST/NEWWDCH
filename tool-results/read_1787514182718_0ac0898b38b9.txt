   130→   130→- Analyzed current editor architecture (3167-line tiptap-editor.tsx):
   131→   131→  - Uses TipTap/ProseMirror as the document model foundation (NOT manual HTML string manipulation).
   132→   132→  - Content saved as HTML in DB; TipTap's setContent() parses HTML → ProseMirror JSON doc; getHTML() serializes doc → HTML. This is the standard TipTap pattern (same as Novel).
   133→   133→  - No dangerouslySetInnerHTML for editor state.
   134→   134→  - Drag reorder uses ProseMirror transactions (tr.delete + tr.insert) — correct, like BlockNote.
   135→   135→  - Selection persistence uses savedSelectionRef {from,to} storing ProseMirror positions (not DOM ranges) — robust, survives focus loss.
   136→   136→  - normalizeContentToHtml() handles legacy ProseMirror JSON stored in DB.
   137→   137→- Compared with reference editors:
   138→   138→  - Tiptap: the current editor IS TipTap-based, so the foundation matches.
   139→   139→  - BlockNote: block-based drag handles via BlockSideMenu — the current DraggableBlocks extension + mousemove-tracked drag handle follows a similar pattern (real DOM handle, ProseMirror transaction reorder).
   140→   140→  - Novel: TipTap-based with bubble menu + slash commands — the current floating toolbar is a bubble-menu equivalent.
   141→   141→  - Lexical: tree-based (different architecture) — not applicable since the project is already TipTap-based; switching to Lexical would be a full rewrite and break the existing CMS.
   142→   142→- Conclusion: The architecture is sound and follows proven TipTap/BlockNote/Novel patterns. No fragile HTML-string manipulation in the editing loop. HTML only appears at the save/load boundary (standard).
