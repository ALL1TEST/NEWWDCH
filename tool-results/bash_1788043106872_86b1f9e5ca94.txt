Stage Summary:
- ENTIRE billing system is now connected to Stripe via secure server-side architecture. Stripe is the source of truth for paid subscription state; our DB mirrors it. No raw card data ever touches our frontend or backend — Stripe Checkout Session is created server-side and the customer is redirected to Stripe-hosted checkout.
- Every paid plan + billing interval in Plans & Pricing maps to a real Stripe Price ID (admin wires the IDs in Edit Plan → Stripe Billing section; checkout reads via resolveStripePriceId and 424-refuses to fake if not wired).
- Stripe webhook handler enforces event-id idempotency via the WebhookEvent ledger (never processes the same evt_... twice across Stripe retries); dedup by stripeInvoiceId + stripePaymentIntentId for payment rows; idempotent cancelSubscription; idempotent coupon-redemption counting. Handles checkout.session.completed, customer.subscription.{updated,created,deleted}, invoice.paid, invoice.payment_failed, payment_intent.{succeeded,payment_failed}, AND NEW charge.refunded.
- Stripe Customer ID, Subscription ID, Invoice ID, PaymentIntent ID, Charge ID stored on Subscription + Payment rows; payment-method metadata (brand/last4/exp/funding/country) stored as JSON on Payment; coupon snapshot (couponCode + discountAmount) on Payment; CouponRedemption per-customer audit; currentPeriodEnd (next billing date); billingInterval; status — all synchronized via webhook events.
- Coupon validation is server-side; per-customer redemption limit enforced via db.couponRedemption.count; local coupons pushed to Stripe as Stripe Coupon + Promotion Code (cached on Coupon.stripeCouponId/stripePromotionCodeId) and applied as `discounts` on the Checkout Session; admin mutation invalidates the Stripe mirror so the next checkout re-creates a fresh one.
